## Confirmed defects

### F1. The wizard keeps the generic webhook URL in sessionStorage (Low)

- Location: `frontend/src/hooks/use-setup.jsx:61`
- Class: secrets at rest in the browser (CWE-922).
- Evidence chain:
  1. `frontend/src/hooks/use-setup.jsx:61` strips notification secrets with `omitSecretKeys`, which
     filters by key name against `SECRET_KEY_RE` (`frontend/src/hooks/use-setup.jsx:28`).
  2. The wizard's Webhook channel stores its URL under the key `url`, which the pattern does not
     match, and the state is written to sessionStorage on every change.
  3. The backend treats that URL as the credential (`CHANNEL_SECRET_FIELDS` in
     `backend/services/config.py`); the existing vitest covers Discord and Telegram only.
- Scenario: an admin starts the wizard on a shared machine, enters an ntfy or Gotify URL with an
  embedded token, and leaves the wizard unfinished; the next user of that browser profile reads
  `panelarr_setup_state` and can post to the admin's notification endpoint.
- Fix approach: persist no notification config (`config: {}`), which the existing test already
  expects for other channel types.
- Reproduction: `frontend/src/hooks/use-setup.audit-2026-11-17.test.jsx`: the F1 case is
  `it.fails` in the normal suite and runs as a plain test with `SWEEP_RUNXFAIL=1` (attack, fails);
  the guard case keeps the non-secret wizard state (passes).
